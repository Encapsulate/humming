# V100 / SM70 baseline

This branch provides an experimental SM70 baseline for a Tesla V100:

- Humming's existing quantization and packing kernels run as JIT CUDA kernels.
- Symmetric, dense, group-128 `uint2`/`uint3` or group-64 `uint4` weights with FP16
  activations use a Volta WMMA kernel. It keeps weights packed in VRAM and
  dequantizes each 16x16 tile on the GPU immediately before tensor-core GEMM.
- That native path accepts FP16 and BF16 group scales, pads the N/K dimensions
  when required, and does not depend on cuBLAS.
- Other compatible dense FP16 configurations use an FP16 dequantized cache
  and PyTorch/cuBLAS for GEMM. The cache is built once by `transform()`, not
  once per forward.

The WMMA path is the appropriate storage model for compatible low-bit GSQ
checkpoints: it avoids a full FP16 weight copy. It is intentionally a simple
correctness-first implementation, so performance tuning and complete
end-to-end model validation remain necessary before production serving. The
FP16 cache fallback expands packed weights and cannot serve large low-bit
checkpoints within a V100's VRAM budget. The upstream SM75+ GEMM is not used
on Volta because it requires `ldmatrix` and `m16n8k16` instructions that SM70
does not implement. MoE, FP8/INT8 activations, asymmetric zero-points, and
weight formats other than the native `uint2`/`uint3` group-128 or `uint4`
group-64 paths remain
unsupported on SM70.

The native GSQ path was validated with PyTorch CUDA 12.1 and CUDA 12.8 on an
SM70 GPU. Use FP16 activations. The cuBLAS fallback still requires a CUDA
runtime whose FP16 GEMM path supports SM70. Install Humming's standard
dependencies in the intended inference environment:

```bash
python -m pip install -e .
python your_program.py
```

If FP16 GEMM fails in a particular PyTorch/CUDA pairing, use a supported
SM70-compatible runtime rather than changing Humming's numerical code.
